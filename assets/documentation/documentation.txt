Chapter I: Hirola Compiler Front End
--------------------------------------------------------------------------------

1. Front End Overview
=====================

The front end of the compiler carries out 2 main operations: lexing and parsing.

During lexing, the written source code is converted into objects called tokens.
The program goes from written source code statements to an array of tokens.
Examples of tokens are "{", "=", ";", keywords and variable names. Errors
are reported if the written program contains unrecognized tokens. Maintained
are the lines and columns at which each token appears, to make error reporting
by the compiler easy to understand and high-quality.

During parsing, the token array is converted into an Abstract Syntax Tree. The
AST contains 1 or more Nodes for each encountered language construct.

For example, the binary operation (a + b) has its own Expression AST Node
containing the sign token and pointers to the AST Nodes of the 2 operands,
which may be BinOps themselves.

Two byproducts are produced during AST construction as well: The Symbol Table
and the Statement Directory.

Two error families are caught and reported during AST construction: syntax ones
such as missing parentheses or semicolons and basic semantic errors, such as
reading a variable that has not yet been initialized.

The AST is placed inside a special hand-managed memory arena, which holds all
the AST Nodes contiguously, in order to boost spatial cache locality for faster
compilation, rather than each AST Node residing in its own small dynamically
allocated memory chunk. This is called data-oriented design and improves the way
modern CPUs are utilized with respect to their microarchitecture. A pointer to
the root AST Node of each source statement is held in the Statement Directory.

Large data structures, such as the Token Array, are transferred from the Lexer
to the Parsing Orchestrator and further ahead via move semantics.

A separate Semantic Analysis pass does not exist yet, but likely will later on.

2. Lexing
=========

The Lexer carries out the operation of turning the written source code program
into an array of tokens. This is the primary output of the Lexer. It also has
1 secondary output as a byproduct - the populated Code Block Directory, which is
simply an array of entries, where each entry gives the starting and ending token
indices and the type of each Code Block.

A Code Block is a building block of the source program, with its start and end
designated with keywords. Examples of Code Blocks: the main source program block
and definitions of functions and custom data types.

Multithreaded compilation, when implemented later on, can be expressed elegantly
as dividing the task of compiling N code blocks between X threads.

Each Token object contains 4 fields:
    - a std::string_view into the source code string where the token appeared;
    - Source code line and column where the token appeared;
    - The token's type.

The Lexer is conceptually a device, so it's represented as a class, much like
the Parser, the IR Generator and other entities that carry out operations.
The Token Array and Code Block Directory get populated by the Lexer and passed
on to the Parsing Orchestrator after lexing finishes.

Token type can be readily deduced from the first character of a lexeme.
All whitespace is ignored. No semantic analysis is performed during lexing.
Minimal errors in the program are caught, namely unrecognized tokens and
improper placement of code within Code Blocks.

3. Parsing
==========

Parsing constructs the AST of a given input source program.

A Parsing Orchestrator is spawned, one per source file. It uses the Code Block
Directory populated by the Lexer to tell one or more Parsers individually which
Code Blocks of the Token Array to parse. This allows for eventually implementing
elegant multithreaded parsing. For the moment, it is singlethreaded.

Byproducts of AST construction: The Statement Directory and Symbol Table.

The Symbol Table is held in a C++ std::unordered_map, with the key being the
actual token name string and the corresponding value being a Symbol object.
Maintaining the Symbol Table in any sorted order is not needed, thus the C++
std::unordered_map is better than an std::map.

Symbols are represented as a class. Each Symbol object contains 4 things:

    - The kind of Symbol this is (function name, variable name, etc)
    - The actual symbol name string;
    - The type of the Symbol. When functions and other primitive types exist,
                              this will be a documented bitfield, with the first
                              few bits giving us the type, any next bits giving
                              us the function signature if it's a function.

    - The symbol's IR mangle counter. This is used in the IR generation phase to
                                      maintain Static Single Assignment form.

The AST is held in a special memory arena of bytes. Each arena slot contains one
AST Node, plus any byte offset its alignment requirements may have incurred.
A special data structure called the Statement Directory contains the byte offset
into the Arena of each source statement, aka of the root of each AST subtree,
completing the whole AST structure.

Each AST Node is represented by its own class. AST Nodes that can be of several
types are repesented by one non-instantiable abstact base class and ONE LAYER of
derived concrete classes for each of this Node's types. For example, Expression
can be a binary_operation, a literal or a symbol, etc.

4. Semantic analysis & error reporting
======================================

Lexing catches and reports basic syntax errors when an unknown symbol is seen,
as well as whether each chunk of source code is within a Code Block.

AST construction catches all other syntax errors, such as missing parentheses
and semicolons, plus basic semantic errors, like a read before initialization.

A fully fledged semantic analysis pass doesn't exist, but likely will later on.

CHAPTER II: Hirola Compiler Middle End
--------------------------------------------------------------------------------

In the compiler middle end, the AST is taken as input and used to generate the
SSA IR code. Similarly to parsing, an IR Generation Orchestrator is spawned per
source file, using a quota (an array of Code Block indices) to spawn one or more
IR Generators and tell them which parts of the AST to emit IR code for.

Similarly to AST construction, the IR instructions go into a special memory
arena, contiguously to boost spatial cache locality and speed up compilation.
The arena byte offset to each IR Instruction is in the IR Instructions Directory
which is the 1 byproduct structure of IR Generation.

Each entry of the IR Instructions Directory contains 4 things:

    - Memory arena offset of the IR Instruction's object;
    - Which source code statement this IR Instruction was emitted for;
    - Which Code Block this source statement was part of;

    - Which IR instruction index this is, in the sequence of IR Instructions
      emitted for this source statement, since a source code statement could
      have multiple IR instructions emitted for it.

Each IR Instruction is represented by its own class.

Each variable's IR mangle counter in its Symbol object is used and incremented
each time a reassignment to that variable is seen when going source statement
by source statement and emitting IR code for each one. For instance, a variable
called my_var which, after its first initializing assignment, is assigned to
2 more times, will appear as %my_var_1, %my_var_2, %my_var_3 in the emitted IR
code. Nested binary operations are stored in auxilliary IR constants called
%const_X, where X is simply how many we've had to use so far.

Since the IR code is in Static Single Assignment form, it lends itself nicely
to many compiler optimizations, such as Loop-invariant code motion, common
subexpression elimination, constant propagation and others. None have been
implemented at present, it's a future effort.

Chapter III: Hirola Compiler Back End
--------------------------------------------------------------------------------


Quick overview
--------------

The compiler back-end transforms SSA IR code into assembly language code.

The end goal is to be able to emit assembly code for both x86_64 and ARM64.
Currently only an x86_64 backend exists and comprises of basic instruction
selection, with no assembly code optimizations or register allocation yet.

The design is to have one Basic Machine Description and multiple Special
Machine Descriptions per instruction set architecture. The Basic one shall
contain just enough of the ISA's instructions, registers and other elements
specified to be able to correctly emit basic assembly language programs for that
ISA. These assembly programs will be able to run on a vast majority of machines,
new and old alike and won't be making use of any particular microarchitecture
generation's specifics, such as 512-bit registers in AVX512 for example.

Special Machine Descriptions will contain microarchitectural details of one
specific CPU architecture generation that will allow for optimizations that are
rooted in how the given source program behaves on that particular architecture.

Details that may be used in such optimization passes include the number of slots
in the micro-op cache in the CPU Frontend (both ARM and x86_64 have one), the
reorder buffer slots, the topology of the micro-op execution ports, availability
of assembly instructions for manual prefetching of data into data caches,
instruction latencies, SIMD vector register availability and more.

Instruction selection, register allocation, assembly code optimization passes,
instruction scheduling are all compiler phases will shall live in the back-end.


Current compiler back-end implementation
----------------------------------------

So far, the compiler supports one backend - x86_64. It has a basic machine
description for this ISA and no special machine descriptions yet. It has one
basic instruction selection phase that simply spills on the stack every
intermediate result and doesn't attempt to optimize the emitted assembly code.

The instruction selection phase works by looking at each IR instruction that
was emitted in the compiler middle-end and looks at a predefined set of patterns
that match a given IR instruction with exactly one assembly code pattern. Later
on, it's likely that one IR instruction or set of IR instructions will have
multiple possible assembly code patterns to be matched with. For now, it is
simply on a per IR instruction basis: One IR instruction -> One assembly code
pattern, period.

Stack space is preallocated at the beginning of a Code Block, since the amount
needed is known at compile time. This is the first assembly instruction emitted
for a given Code Block: sub rsp, <stack_bytes_needed>

One assembly code optimization that is already implemented is omitting the usage
of the RBP register in x86_64. Traditionally, this register was used as an
anchor point that always points to the beginning of the current stack frame,
where the RSP register points at the end of it. However, all we need in order to
access anything on the stack frame is the RSP register itself, RBP isn't a
mandatory piece of information. Thus, RBP is free to be used as just another
general purpose register in the compiler backend, it is NOT used for stack
frame management.

A general purpose C++ class was written to represent any assembly instruction.
This class always contains the maximum number of instruction operands,
regardless of how many operands a particular emitted assembly instruction
happens to need. This makes the compiler backend codebase more compact. The
alternative is to have one class representing each different instruction in the
ISA, or even one class to represent each form of each assembly instruction. This
would bloat the backend codebase by a lot, so for now, we will stick with the
one generic x64_Assembly_Instruction C++ class and simply leave empty any
unused operand fields.

That class has a member function for writing the actual assembly language code
string for a given instruction and its operands to a file. The function takes
a single input argument: the file descriptor to write assembly code to.

Some general info regarding i/o on FILE* objects vs i/o on file descriptors:

For a real file accessed through a FILE*, one can grab its file descriptor using
fileno(my_FILE_ptr) and pass that file descriptor to the assembly code emitting
function. The reverse operation exists too. Since a FILE* lets you do useful
things like fgets(), fprintf(), etc, you can take an existing file descriptor
and wrap it in a FILE* object using fdopen(int fd, const char *mode).
Low-latency code tends to stay away from FILE* and work on file descriptors
directly, using the read() and write() GNU/Linux system calls.

Assembly instructions that have C++ code to emit them in more than one place
across the compiler codebase get their own "factory functions", so that the
several lines of code needed to construct the instruction object, along with
its operand objects and the necessary compiler bookkeeping needed are replaced
with a single function call. The ASM_Code_Generator_x64 class contains these
as private member functions.

So far only two instruction formats have a factory function:

1. mov reg, [reg + offset_immed]
2. mov [reg + offset_immed], reg

The rest of the currently supported assembly instructions in the x86_64 Basic
Machine Description have one emission site for one instruction format, so they
are emitted on the spot without a wrapper function.

Compile-time lookup tables with named indices are used for:

    - Mnemonics of supported assembly instructions
    - Names of supported architectural registers

These make the C++ code prettier when selecting registers and instructions.


x86_64 Instruction Selection
----------------------------

Instruction Selection itself is carried out when the top-level compiler driver
spawns an Assembly Code Generation Orchestrator, which in turn spawns one or
more Assembly Code Generators, which are each handed one job quota. A job quota
is simply a set of code block indices giving the code blocks to emit assembly
instructions for. The set of sets that contains all job quotas is handed to the
Assembly Code Generation Orchestrator by the top-level compiler driver.

This follows the design of the AST construction and the SSA IR code generation
phases. When the language eventually gains the ability to have multiple Code
Blocks, the compiler's work will be elegantly split across them - for example,
4 threads and 8 Code Blocks, we can get each thread to emit AST Nodes, SSA IR
code and Assembly code for 2 Code Blocks.

GNU/Linux SysV ABI is the one to be followed. GNU Assembler (GAS) is the
assembler of choice. Assembly programs can be emitted only for GNU/Linux OS.

Instructions are selected via predefined pattern matching. Every single IR code
to Assembly code pattern has its own instruction selection function.

All current IR code --> Assembly code patterns:

| 4. Store register rbp in var1's stack offset. |  mov [rsp + offset1], rbp  |

|----------------------------------------------------------------------------|
| MULTIPLICATION                                                             |
|----------------------------------------------------------------------------|
| Pattern 4:   { %_temp_1 = %a_2 * %a_3 }  --->  IR_var1 = IR_var2 * IR_var3 |
|                                               -----------------------------|

| 2. Store var3 in rax from its stack offset.   |  mov rax, [rsp + offset3]  |
| 3. Multiply. RAX * Operand2 = RDX:RAX <-- low |  mul rax, rbp              |
| 4. Store register rax in var1's stack offset. |  mov [rsp + offset1], rax  |
|----------------------------------------------------------------------------|
| NOTE: This is UNSIGNED multiplication. If the result needs to use more     |
|       than 64 bits, the higher bits go to RDX and the overflowed low bits  |
|       are in RAX. The first operand is always RAX, second one - we pick.   |
|----------------------------------------------------------------------------|


|----------------------------------------------------------------------------|
| DIVISION                                                                   |
|----------------------------------------------------------------------------|
| Pattern 5:   { %_temp_1 = %a_2 / %a_3 }  --->  IR_var1 = IR_var2 / IR_var3 |
|                                                ----------------------------|
| 1. Store var2 in RAX from its stack offset.    | mov rax, [rsp + offset2]  |
| 2. Sign-extend RAX into RDX to run division.   | cqo                       |
| 3. Store var3 in rbp from its stack offset.    | mov rbp, [rsp + offset3]  |
| 4. Divide RDX:RAX / Operand2 = RDX:RAX <-- low | div rbp                   |
| 5. Store register rax in var1's stack offset.  | mov [rsp + offset1], rax  |
|----------------------------------------------------------------------------|
| NOTE: This is UNSIGNED division. The quotient goes in RAX, the remainder   |
|       goes in RDX, which is why we sign-extend RAX into RDX beforehand.    |
|       What we divide is in RAX. What we divide by is in a register or a    |
|       memory location of our choosing.                                     |
|----------------------------------------------------------------------------|


x86_64 Basic Machine Description
--------------------------------

1. Supported instructions: 7

mov, add, sub, mul, div, cqo, syscall

2. Supported registers: 32

    - rax, rbx, rcx, rdx
    - r8 to r15
    - rdi, rsi
    - rsp, rbp
    - xmm0 to xmm15

3. Machine Word Size = 8 bytes

4. Maximum number of operands per instruction: 4

5. Instruction operand formats: 6

    - x64_operand_type_immediate
    - x64_operand_type_reg
    - x64_operand_type_reg_as_ptr
    - x64_operand_type_reg_plus_immed_as_ptr
    - x64_operand_type_complex_array_elem_access
    - x64_operand_type_label


System V AMD64 ABI conventions implemented
------------------------------------------

1. First 6 INTEGER function arguments are passed in: rdi, rsi, rdx, rcx, r8, r9
2. First 8 FLOAT   function arguments are passed in: xmm0 - xmm7

3. Functions return an integer in RAX.
4. Functions return a floating point value in XMM0.

5. Functions returning a struct shall be given a pointer to a pre-allocated by
   the CALLER memory area in rdi. The callee that's actually returning a struct
   shall use the pointer in rdi to write out the struct itself to memory when
   returning it. Lastly, the callee places the same pointer in rax before RET.

6. Six callee-saved registers: rbx, rbp, r12, r13, r14, r15
7. Caller-saved registers: All the rest.

8. Stack pointer register RSP alignment requirement: 16 bytes

   The RSP register must be divisible by 16 before a CALL instruction runs.
   If it's not, emit a {sub rsp, N} instruction.

   IMPORTANT: The OS gives us a guarantee that RSP will be aligned to 16 bytes
              when it spawns a process out of our assembly program. We just have
              to make sure that's still so before all emitted CALL instructions.

              CALL instructions automatically push the return address on stack,
              so RSP is divisible by 8 right after a CALL instruction runs.

Chapter IV. Custom data structures implemented for the compiler
--------------------------------------------------------------------------------

In this chapter we go over the special hand-written C++ data structures used by
the compiler implementation.

Quick overview:
---------------

There is currently 1 special data structure used across compiler phases:

    - Custom memory arena

1. Custom Memory Arena
----------------------

This is simply a byte buffer wherein different-sized, but related, objects ought
to be populated. The aim is to boost spatial cache locality, thus speeding up
compilation itself.

Examples where it's used: To store the AST Nodes, as well as to store each
                          emitted IR instruction for a given source program.

The alternative, for the AST Nodes, would be to let each AST Node be in its own
small heap-allocated chunk, which is what std::map does in C++. This could more
inefficiently make use of modern CPU microarchitecture, as the hardware prefetch
machinery in modern CPUs assumes that nearby memory locations (nearby cache
lines, to be precise) are likely to be required, and recognizes memory access
patterns such as quick accesses to cache lines N, N+1, N+2 and automatically
starts prefetching the contents of the following cache lines into the hardware
caches, so that when you do need their contents, they are already sitting in
the cache, saving you cycles you would have otherwise spent waiting for this
data to arrive from RAM, which is much slower than fetching the data from cache.

C++ templates were used to implement the add_entry function for the arena. A
template type T generalized the new entry's type, and a variadic template is
used to generalize on the arity and types of arguments given, which are to be
passed to the constructor of the newly added arena entry.
