OVERVIEW OF THE DOCUMENTATION
=============================

All essential information about the Hirola language compiler, the project
itself, the directory and file structure and their contents are found here.

This document is divided into 4 main chapters describing, respectively, the
compiler's three primary subsystems: front end, middle end and back end, as well
as a chapter dedicated to the custom C++ data structures implemented to be used
throughout the compiler's implementation.

A separate document describes various optimizations and contains writeups of
CPU microarchitecture-aware performance analyses conducted on the compiler.

Chapter I: Hirola Compiler Front End
--------------------------------------------------------------------------------

1. Front End Overview
=====================

The front end of the compiler carries out 2 main operations: lexing and parsing.

During lexing, the written source code is converted into objects called tokens.
The program goes from written source code statements to an array of tokens.
Examples of tokens are "{", "=", ";", keywords and variable names. Errors
are reported if the written program contains unrecognized tokens. Maintained
are the lines and columns at which each token appears, to make error reporting
by the compiler easy to understand and high-quality.

During parsing, the token array is converted into an Abstract Syntax Tree. The
AST contains 1 or more Nodes for each encountered language construct.

For example, the binary operation (a + b) has its own Expression AST Node
containing the sign token and pointers to the AST Nodes of the 2 operands,
which may be BinOps themselves.

Two byproducts are produced during AST construction as well: The Symbol Table
and the Statement Directory.

Two error families are caught and reported during AST construction: syntax ones
such as missing parentheses or semicolons and basic semantic errors, such as
reading a variable that has not yet been initialized.

The AST is placed inside a special hand-managed memory arena, which holds all
the AST Nodes contiguously, in order to boost spatial cache locality for faster
compilation, rather than each AST Node residing in its own small dynamically
allocated memory chunk. This is called data-oriented design and improves the way
modern CPUs are utilized with respect to their microarchitecture. A pointer to
the root AST Node of each source statement is held in the Statement Directory.

Large data structures, such as the Token Array, are transferred from the Lexer
to the Parsing Orchestrator and further ahead via move semantics.

A separate Semantic Analysis pass does not exist yet, but likely will later on.

2. Lexing
=========

The Lexer carries out the operation of turning the written source code program
into an array of tokens. This is the primary output of the Lexer. It also has
1 secondary output as a byproduct - the populated Code Block Directory, which is
simply an array of entries, where each entry gives the starting and ending token
indices and the type of each Code Block.

A Code Block is a building block of the source program, with its start and end
designated with keywords. Examples of Code Blocks: the main source program block
and definitions of functions and custom data types.

Multithreaded compilation, when implemented later on, can be expressed elegantly
as dividing the task of compiling N code blocks between X threads.

Each Token object contains 4 fields:
    - a std::string_view into the source code string where the token appeared;
    - Source code line and column where the token appeared;
    - The token's type.

The Lexer is conceptually a device, so it's represented as a class, much like
the Parser, the IR Generator and other entities that carry out operations.
The Token Array and Code Block Directory get populated by the Lexer and passed
on to the Parsing Orchestrator after lexing finishes.

Token type can be readily deduced from the first character of a lexeme.
All whitespace is ignored. No semantic analysis is performed during lexing.
Minimal errors in the program are caught, namely unrecognized tokens and
improper placement of code within Code Blocks.

3. Parsing
==========

Parsing constructs the AST of a given input source program.

A Parsing Orchestrator is spawned, one per source file. It uses the Code Block
Directory populated by the Lexer to tell one or more Parsers individually which
Code Blocks of the Token Array to parse. This allows for eventually implementing
elegant multithreaded parsing. For the moment, it is singlethreaded.

Byproducts of AST construction: The Statement Directory and Symbol Table.

The Symbol Table is held in a C++ std::unordered_map, with the key being the
actual token name string and the corresponding value being a Symbol object.
Maintaining the Symbol Table in any sorted order is not needed, thus the C++
std::unordered_map is better than an std::map.

Symbols are represented as a class. Each Symbol object contains 4 things:

    - The kind of Symbol this is (function name, variable name, etc)
    - The actual symbol name string;
    - The type of the Symbol. When functions and other primitive types exist,
                              this will be a documented bitfield, with the first
                              few bits giving us the type, any next bits giving
                              us the function signature if it's a function.

    - The symbol's IR mangle counter. This is used in the IR generation phase to
                                      maintain Static Single Assignment form.

The AST is held in a special memory arena of bytes. Each arena slot contains one
AST Node, plus any byte offset its alignment requirements may have incurred.
A special data structure called the Statement Directory contains the byte offset
into the Arena of each source statement, aka of the root of each AST subtree,
completing the whole AST structure.

Each AST Node is represented by its own class. AST Nodes that can be of several
types are repesented by one non-instantiable abstact base class and ONE LAYER of
derived concrete classes for each of this Node's types. For example, Expression
can be a binary_operation, a literal or a symbol, etc.

4. Semantic analysis & error reporting
======================================

Lexing catches and reports basic syntax errors when an unknown symbol is seen,
as well as whether each chunk of source code is within a Code Block.

AST construction catches all other syntax errors, such as missing parentheses
and semicolons, plus basic semantic errors, like a read before initialization.

A fully fledged semantic analysis pass doesn't exist, but likely will later on.

CHAPTER II: Hirola Compiler Middle End
--------------------------------------------------------------------------------

In the compiler middle end, the AST is taken as input and used to generate the
SSA IR code. Similarly to parsing, an IR Generation Orchestrator is spawned per
source file, using a quota (an array of Code Block indices) to spawn one or more
IR Generators and tell them which parts of the AST to emit IR code for.

Similarly to AST construction, the IR instructions go into a special memory
arena, contiguously to boost spatial cache locality and speed up compilation.
The arena byte offset to each IR Instruction is in the IR Instructions Directory
which is the 1 byproduct structure of IR Generation.

Each entry of the IR Instructions Directory contains 4 things:

    - Memory arena offset of the IR Instruction's object;
    - Which source code statement this IR Instruction was emitted for;
    - Which Code Block this source statement was part of;

    - Which IR instruction index this is, in the sequence of IR Instructions
      emitted for this source statement, since a source code statement could
      have multiple IR instructions emitted for it.

Each IR Instruction is represented by its own class.

Each variable's IR mangle counter in its Symbol object is used and incremented
each time a reassignment to that variable is seen when going source statement
by source statement and emitting IR code for each one. For instance, a variable
called my_var which, after its first initializing assignment, is assigned to
2 more times, will appear as %my_var_1, %my_var_2, %my_var_3 in the emitted IR
code. Nested binary operations are stored in auxilliary IR constants called
%const_X, where X is simply how many we've had to use so far.

Since the IR code is in Static Single Assignment form, it lends itself nicely
to many compiler optimizations, such as Loop-invariant code motion, common
subexpression elimination, constant propagation and others. None have been
implemented at present, it's a future effort.

Chapter IV. Custom data structures implemented for the compiler
--------------------------------------------------------------------------------

In this chapter we go over the special hand-written C++ data structures used by
the compiler implementation.

Quick overview:
---------------

There is currently 1 special data structure used across compiler phases:

    - Custom memory arena

1. Custom Memory Arena
----------------------

This is simply a byte buffer wherein different-sized, but related, objects ought
to be populated. The aim is to boost spatial cache locality, thus speeding up
compilation itself.

Examples where it's used: To store the AST Nodes, as well as to store each
                          emitted IR instruction for a given source program.

The alternative, for the AST Nodes, would be to let each AST Node be in its own
small heap-allocated chunk, which is what std::map does in C++. This could more
inefficiently make use of modern CPU microarchitecture, as the hardware prefetch
machinery in modern CPUs assumes that nearby memory locations (nearby cache
lines, to be precise) are likely to be required, and recognizes memory access
patterns such as quick accesses to cache lines N, N+1, N+2 and automatically
starts prefetching the contents of the following cache lines into the hardware
caches, so that when you do need their contents, they are already sitting in
the cache, saving you cycles you would have otherwise spent waiting for this
data to arrive from RAM, which is much slower than fetching the data from cache.

C++ templates were used to implement the add_entry function for the arena. A
template type T generalized the new entry's type, and a variadic template is
used to generalize on the arity and types of arguments given, which are to be
passed to the constructor of the newly added arena entry.
